Nitpicker

Nitpicker reads your ticket, plan, or article the way a smart newcomer would. They have only the text and the repo, they do exactly what the text says, and they can't ask you anything. Every spot where they would have to guess becomes a question for you, ranked by how costly a wrong guess would be.

> /nitpicker DAS-2516
Real run · DAS-2516 · lines quoted from the ticket

Operators see and edit every pair's settings in the BO

Using a pool address that another pair already uses shows a warning; saving is still allowed1.

After saving, the BO says the change reaches live prices within about 5 minutes2.

Edit is hidden without price-oracle:settings:write3; the server refuses an update without it.

Bench: staging BO4. Checked: … config export shows the new value.

A base58 address is saved exactly as entered; an EVM address may be normalised5.

1
Allow a reused pool, when the database forbids it?
A unique index on (sourceId, poolAddress) at oracle-config.ts:198 blocks every save of this kind. This was the cause of the QA failure DAS-2799.
2
Show this before the live-config ticket is on?
The ticket's own Feature flag section says live prices don't read the BO yet, so until then the message isn't true.
3
This name, or the code's oracle:currencies:write?
The code's permission also allows creating pairs (oracle-config.controller.ts:274), which the ticket treats as separate work.
4
Do the Integration QA results count as the Proof?
QA ran on bo-integration, and its summary doesn't mention the export diff.
5
Lowercase, checksummed, or as entered?
Non-blocking, but the choice decides whether the same pool in different letter case counts as a reuse.

Nitpicker found these after QA had already passed 11 of 12 test cases. Each blocking note is a place where the ticket and the code disagree, or where the ticket doesn't define done.

How it reads

Certain phrases hide a decision

Nitpicker reads the whole text once, then again sentence by sentence. For each sentence it asks what the reader would have to decide alone. These patterns get flagged on sight. It checks the repo and linked docs for answers first, and attaches what it finds as evidence. It still asks you, because the code shows what exists, and only you know what you intend.

Vague words

should · just · simply · as needed · appropriately
Who decides, and by what rule?

"Follow the pattern"

like we do elsewhere · the usual way
Which file and function? If there are several candidates, or none, that's a question.

Named things

files · symbols · commands · config keys · people
Does each one exist? A missing one blocks the work.

Lists and inputs

the users · the payload · each row
What if it's empty, missing, duplicated, or malformed?

Boundaries

calls the API · runs nightly · writes to the DB
What happens on failure, timeout, concurrent use, or a second run?

Tests

add tests · make sure it works
Which tests, which command, what expected output?

Scope words

all · every · the relevant
What do they actually cover? It counts them and checks whether the number surprises you.

Fuzzy "done"

works · looks right · is clean · is faster
What would you see when it's done?

Reader gaps in prose

acronyms · "next week" · "the team" · "it"
Which team, which date and timezone, and what does "it" refer to?
Ranking

Two piles: blocking and non-blocking

Not every gap matters equally. Questions are ranked by what a wrong guess would cost, highest first. Similar questions are merged so you answer each decision once.

Blocking A wrong guess changes the work

  • Different files or systems get touched
  • A different interface or data shape
  • A different definition of done
  • Hard to undo: migrations, deletions, anything sent or published
  • Runs unattended on the guess: cron jobs, automations, agents

Non-blocking Cheap to fix in review

  • Naming, wording, and small defaults
  • Error messages and log text
  • Anything a reviewer would catch in one comment

Add --blocking-only to skip these when you only need to know whether work can start.

Output

Three modes, one for each kind of text

Name a mode, or leave it out and Nitpicker picks one from the input and tells you which.

ticket

Questions for the author, plus recommendations

A short list you can answer in one sitting. It's split into "must answer before work starts" and "worth answering", followed by concrete things to add to the ticket.

Auto-picked for Linear IDs and anything shaped like a work item. It can post the questions as a ticket comment, but only if you say yes.

> /nitpicker ticket DAS-2516
# Questions before this is ready: DAS-2516 (real run, shortened)
Verdict: Not ready to close: 4 blocking questions

## Must answer before work starts
1. Should a reused pool address be allowed,
   given the database forbids it?
   Why: allowing it needs a migration; forbidding
   it changes the AC and the warning text
   Found: oracle-config.ts:198 unique index;
   QA failure DAS-2799
2. Show "live within ~5 min" before the
   live-config ticket is switched on?
3. Ticket's permission names, or the code's?

## Worth answering
- Scope says dapps; PR #20 is in the backoffice repo

## Recommendations
- Update Decision: None with the 29 Sep and
  3 Nov decisions
- Fill in Files and Size from PR #20
text

An accept/reject page for prose

An interactive page with each flagged snippet, what's unclear, and an editable suggested rewrite with a checkbox. A live preview shows the revised text. You can copy or download it, or copy your decisions and paste them back to Claude to apply.

Auto-picked for articles, blog posts, doc pages, announcements, READMEs, and emails.

> /nitpicker text drafts/launch-post.md

Example cards. Try the checkboxes. Decisions that need you show up as [brackets] for you to fill in. Nitpicker never guesses them.

report

A full ranked review with evidence

For implementation plans and specs, especially ones going to an AI agent or someone who won't be able to ask. Each question comes with where it is in the text, why it blocks, evidence from the repo, and which other questions its answer settles. At the end is a list of references it checked and found.

Auto-picked for plans and specs written against a repository.

> /nitpicker report plans/scheduler-migration.md
# Nitpicker review: Scheduler migration (example)

  billing job double-charges if it runs

Learns from every run

Each finding becomes a rule for next time

A review fixes one ticket. After each run, Nitpicker turns its findings into rules about how to write, not about what was written. Each rule names a kind of sentence and what it must always include. It asks before saving them. Its partner skill, no-loose-ends, applies the rules when writing the next ticket, plan or article.

Finding

"The new dashboard rolls out next week." Readers can't tell which day it is, or whether it's about them.

Kind of sentence: an announcement of a change
Missing: the date, and who it affects

Rule it became

When you announce a change, always include the exact date and who it affects.

It applies to a release note, a holiday email or a migration ticket alike, because it's about the sentence, not the subject.

Personal rules

Saved to your machine after you say yes. Each rule tracks how many times its gap has been seen.

Team rules

Bundled with no-loose-ends and changed by PR. A personal rule seen 3+ times gets suggested for the team file.

Writing with them

Ask "write a ticket for…" and no-loose-ends applies the rules, checks the draft against them, and lists open questions instead of guessing.

CommandWhat it does
/nitpicker rulesLists your rules and the team rules with Seen counts, and flags ones ready for the team, possible duplicates and stale rules.
/nitpicker rules show <title>Shows one rule in full.
/nitpicker rules promote --readyDrafts a PR adding every personal rule seen 3+ times to the team file. It asks before pushing.
/nitpicker rules remove <title>Deletes a personal rule, or offers a removal PR for a team rule.

Ground rules

What it won't do

Guess for you

It shows evidence, but you make the decision. Anything it can't settle from the text becomes a question or a [placeholder].

Edit on its own

It doesn't change tickets, files, or code until you accept changes, and it never posts a comment you didn't ask for.

Invent nitpicks

If the text is clear, you get a short "ready" verdict. Empty sections are a valid result.

Get it

Install

Nitpicker is a plugin in the paula-tools marketplace. Add the marketplace once, then install the plugin. After that, run /nitpicker:nitpicker and /nitpicker:no-loose-ends, or just ask in plain words, like "nitpick DAS-1234" or "write a ticket for…". The short commands on this page are written without the nitpicker: prefix.

> /plugin marketplace add paufar/paula-tools-marketplace
> /plugin install nitpicker@paula-tools
Linear tickets

Passing a ticket ID like DAS-1234 needs a Linear connection in Claude Code, for example through Anthropic's engineering plugin, which our org provides. Without one, paste the ticket text instead.

Accept/reject pages

text mode publishes a private page to your claude.ai account. Share it from the page's Share menu.

Evidence from code

Run it from a folder that contains the repo, so it can check file names, permissions and schemas against the ticket.
