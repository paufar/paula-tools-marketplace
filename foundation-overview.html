AI Project Foundation

The templates I copy into a new project during initialization. This page explains the setup and why each file is in it.

Why it exists

A coding agent has no memory between sessions and no view of the decisions behind the code. Left alone it guesses, and the guesses compound. Two failures follow:

  • Vibe-coding collapse. The agent invents structure as it goes, then contradicts itself.
  • Feature drift. Weeks later the agent has forgotten the conventions and "fixes" things that were deliberate.

The foundation fixes both by putting the thinking in files. I decide what is built, how, and what the rules are. The agent reads those files first, every session, and executes.

How a session runs

Clock in

Read PROGRESS.md and DECISIONS.md, run make check, continue from "Next Steps".

Work

One feature unit at a time, against the context docs. No invented behaviour.

Clock out

Update PROGRESS.md with evidence, log decisions, run make check, commit.

Installing the plugins

/plugin marketplace add paufar/paula-tools-marketplace
/plugin install project-foundation@paula-tools
/plugin install learning-tools@paula-tools

Skills are then invoked with the plugin name as a prefix: /project-foundation:init-project, /project-foundation:test-me, /learning-tools:interview-prep, /learning-tools:close-session. In the rest of this page, templates/ means plugins/project-foundation/templates/.

Entry files

Below are the entry files in templates/, which are copied into projects. The repo root also has its own AGENTS.md and CLAUDE.md with the rules for maintaining this template repo. Those are never copied. Only the contents of templates/ go into a project.

AGENTS.md committed

templates/AGENTS.md
Holds
Project overview, tech stack and versions, first-run commands, hard constraints, a map of the context docs, and the clock in / clock out routine.
Why it exists
It is the one file the agent is told to read first. It stays short and points to detail elsewhere, so the agent reads only what the task needs.
Without it
The agent skips the context docs and guesses.
Updated
When the stack, commands or hard constraints change.

CLAUDE.md committed

templates/CLAUDE.md
Holds
A short instruction to read AGENTS.md and follow it every session.
Why it exists
Claude Code looks for CLAUDE.md; other agents look for AGENTS.md. The pointer keeps one source of truth.
Updated
Almost never.

Makefile committed

templates/Makefile
Holds
A single make check target. The stub fails on purpose until replaced with real lint, type-check, test and build commands.
Why it exists
Clock in and clock out both need one command that answers "is the repo consistent?". The agent should not have to work out which commands to run.
Updated
Once at setup, then whenever a check is added or removed.

Context docs

All in context/, all committed. Each is capped at 100 - 150 lines once filled in.

PROJECT.md

Holds
Overview, goals, core user flow, features, in and out of scope, success criteria.
Why it exists
Defines what is being built, so the agent never invents product behaviour.
Updated
When scope changes.

ARCHITECTURE.md

Holds
Stack and roles, system boundaries per folder, storage model, auth and access model, invariants.
Why it exists
Defines how the system fits together and the rules that must never be broken. Invariants are referenced from the hard constraints in AGENTS.md.
Updated
When boundaries, storage or auth change.

UI-CONTEXT.md

Holds
Theme, colour tokens, typography, radius scale, component library, layout patterns, icons.
Why it exists
Keeps the interface consistent across sessions. Without tokens the agent hardcodes values and each screen drifts.
Updated
When the design language changes.

CODING-STANDARDS.md

Holds
Rules per area: general, language, framework, styling, API routes, data, file organisation.
Why it exists
Defines how code is written, so output matches the existing codebase rather than the agent's defaults.
Updated
When a convention is added or changed.

AI-WORKFLOW-RULES.md

Holds
Development approach, scoping rules, the work in progress limit (1), when to split work, how the agent should work with me (explanation style, tools to prefer), handling missing requirements, protected files, the checklist before moving to the next unit.
Why it exists
Governs how the agent works: one task at a time, small verifiable steps, no invented requirements, docs kept in sync.
Updated
When the process changes, and when protected files are added.

PROGRESS.md

Holds
Current phase and goal, Done, In Progress, Blocked, Next Steps, open questions, session notes. Every item has a checkable "Done when", and at most one item is In Progress (WIP limit 1).
Why it exists
It is the agent's memory. The agent clocks in from it and clocks out by updating it. An item moves to Done only with evidence.
Updated
Every session.

DECISIONS.md

Holds
Dated decisions with reasoning and what they supersede.
Why it exists
Keeps the why behind choices so the agent does not undo them, and keeps PROGRESS.md free of reasoning.
Updated
Whenever a non-obvious decision is made.

Feature specs go in context/specs/ (one per unit, 00-build-plan.md first). The folder is created per project and is not part of the templates.

Local docs

In local-docs/, gitignored. They are for humans, so AGENTS.md does not reference them.

goal.md private

templates/local-docs/goal.md
Holds
What I want to get out of the project for myself: goals, learning targets (skill, tool or plugin, current and target level), how I want the agent to help, boundaries, how I will know it worked, and a "Cleared for Public Files" table.
Why it exists
I often use a project to learn something. The skill reads this file first so its options and questions fit that. The table is the only route into committed files: each approved row is distilled into agent-directed wording (for example in AI-WORKFLOW-RULES.md), free of personal detail. Everything else stays private.

setup.md gitignored

templates/local-docs/setup.md
Holds
Prerequisites, environment variables, install, database, run, verify, everyday commands, deployment, troubleshooting.
Why it exists
Gets a clean machine to a passing make check, and is where to look when setup breaks.

architecture.html gitignored

templates/local-docs/architecture.html
Holds
An illustrated expansion of ARCHITECTURE.md: diagram, flows, storage and data model, invariants with reasons, and an entry for every package, plugin, tool and external service with why it was chosen.
Why it exists
Lets me return after months and see what is used and why. ARCHITECTURE.md wins if the two disagree.

Rules that apply everywhere

RuleReason
Each markdown template is 100 - 150 lines once filled inA short file gets read in full. Overflow moves to a linked doc.
local-docs/ is gitignored and not mentioned in AGENTS.mdThe links would break on a fresh clone, and the agent does not need them.
goal.md is private: only items cleared in its table reach committed files, in distilled wordingPersonal learning goals are not the project's business. Agents still get the guidance that helps them.
Work in progress limit is 1One unfinished task at a time keeps PROGRESS.md honest and every change verifiable.
Nothing is Done without evidence"Works" is not a condition. A command or an observable behaviour is.
Change the doc before the code drifts from itStale docs are worse than none.
When a template changes, update this page and every other affected file in the same changeThis page and the README describe the templates. If they lag, they mislead. The checklist is in the root AGENTS.md.

Using it: the init-project skill

Initialization is a skill, not a checklist. Open Claude Code in a new or existing project and run /project-foundation:init-project. It is user-invoked only, so the agent never fires it on its own.

init-project plugin skill

plugins/project-foundation/skills/init-project/SKILL.md, SECTIONS.md, EXISTING.md
Modes
New for an empty project. Existing when the project already has markdown docs: their useful content prefills the templates and the old files are retired.
Tracker
project-initialization.md in the project root shows the status of every step and every file being filled in (Pending, In progress, Done, Skipped, plus Drafting, Approved and Deferred for files). It is created after step 1, updated at every step, and deleted at the end. If a run stops early it stays. /init-project resume picks up where it stopped, and plain /init-project asks whether to resume or start over.
Steps
1. Confirm the target directory and mode, then create the tracker.
2. Existing only: read every markdown file, and agree a table of file, what it holds, which template sections it feeds, and its fate (absorb and delete, keep, ignore).
3. Copy the contents of templates/ and create context/specs/. Existing files with a template's name are moved to .init-project-old/, not overwritten.
4. Add local-docs/ to .gitignore.
5. Fill in every template with me (below).
6. Existing only: check nothing useful is left behind, then delete the absorbed files after I confirm.
7. Verify: no stray placeholders, 100 - 150 lines per file, make check is real, at most one item in progress.
8. Hand over a summary and delete the tracker. It does not commit.
How it fills in
File by file, in dependency order: the private goal.md first (it shapes the options offered for everything after it), then PROJECT, ARCHITECTURE, UI-CONTEXT, CODING-STANDARDS, AI-WORKFLOW-RULES, AGENTS, Makefile, PROGRESS, DECISIONS, the build plan and first spec, then local-docs/. Only the parts of goal.md I clear are turned into agent guidance in committed files. Content that already exists is shown first, labelled with the file it came from, and I choose to use it, edit it or replace it. Otherwise it asks one question at a time, offers options with a recommendation, and lets me pick, answer freely, skip or defer. Skipped sections become Open Questions in PROGRESS.md.
Why it exists
The same steps every time, I make the decisions instead of staring at blank templates, and an existing project keeps its knowledge instead of losing it. SECTIONS.md holds the questions per file. EXISTING.md holds where old content goes and the delete-or-keep rules. Each is read only when needed.
Where it lives
In the project-foundation plugin, installed from the paula-tools marketplace, so it is available in every project. It reads the templates from the plugin's own templates/ folder (${CLAUDE_PLUGIN_ROOT}/templates, set at the top of SKILL.md). The skill and the templates live in the same repo, so a template change and the skill change go in one commit.

Testing the goals: the test-me skill

The other half of goal.md. Run /project-foundation:test-me in a project when it is time to find out whether I achieved what I set out to. User-invoked only.

test-me plugin skill

plugins/project-foundation/skills/test-me/SKILL.md
Steps
1. Load local-docs/goal.md and the project's context docs and code, so questions rest on real things.
2. Set the ground rules: one question at a time, no hints, vague answers get pushed on, skipped goals are recorded as not tested.
3. Grill goal by goal, climbing a ladder from recall to explain, apply, predict, diagnose and defend, until my ceiling appears. Doing goals get a small applied task that I do myself.
4. Judge each goal: Reached, Partly, Not yet or Not tested, with evidence and the level shown for each learning target.
5. Report, then, with my OK, append the result and next steps to the Notes in goal.md.
6. Say what to work on, and offer to retest the goals not reached.
Why it exists
Feeling that I learned something is not evidence. The skill checks my answers against the code and grades what I demonstrated, not my confidence.
Privacy
Results go only into goal.md. It never edits committed files and never commits.

Before an interview: the interview-prep skill

Works on any repo, and uses goal.md when it is there. Run /learning-tools:interview-prep in any repo, optionally with a vacancy (URL, file or pasted text). User-invoked only.

interview-prep plugin skill

plugins/learning-tools/skills/interview-prep/SKILL.md
Steps
1. Take in the vacancy: role, seniority and the few things it cares about most.
2. Learn the project from evidence: decision docs, dependencies, code and git history, plus goal.md for the areas I was already shaky on. Every claim is labelled documented, visible or inferred, and an unrecorded reason is never invented.
3. Brief me: the 30-second pitch, architecture decisions with trade-offs, tools and why, honest weak spots, and a map from the vacancy to the project including gaps.
4. Mock interview, one question at a time, weighted towards the vacancy, with brief coaching or none (my choice). Claims are checked against the code.
5. Debrief: strong and shaky answers, sharper phrasing, stories to have ready, a re-read checklist.
6. With my OK, save the briefing and debrief to local-docs/interview-notes.md. Offer a second round.
Why it exists
A refresher before an interview, built from what the project really shows, so I can explain my decisions in my own words instead of recalling them cold.
Privacy
It reads goal.md but never quotes it outside local-docs/. It writes only to the gitignored local-docs/interview-notes.md (it uses git check-ignore and refuses to write if the path is not ignored or is already tracked), never edits goal.md or .gitignore, and never stages or commits anything, even if asked.

Ending a session: the close-session skill

Works on any session, project-related or not. Run /learning-tools:close-session when stopping, optionally with a focus. User-invoked only.

close-session plugin skill

plugins/learning-tools/skills/close-session/SKILL.md
Steps
1. Gather from the conversation what the session was about, what was done and decided, and what failed. Run git status or git diff --stat only to confirm facts.
2. Write tmp/SESSION_SUMMARY.md (creating tmp/ if needed) with topic, what happened, state right now, decisions, dead ends, open questions, open items and to-dos (even if not yet project tasks), next steps and how to resume. Earlier sections are kept, newest first.
3. Check tmp/ is gitignored and warn if not.
4. Reply with the path and a three-line recap.
Why it exists
A session can be about anything, so its hand-off does not belong in PROGRESS.md, which records the project only. This note lets me or a fresh agent resume cold.
Privacy
It never edits PROGRESS.md, .gitignore or any project file, never stages or commits, and keeps secrets out of the summary.
